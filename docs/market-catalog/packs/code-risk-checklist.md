# 代码风险自查清单（市场包）

适用：提交、提测、评审前对**自己写的代码**做一遍系统性过单。条目按事故率排序，
每一条都对应一类反复发生的线上事故。用法：逐项问「我的改动碰到这条了吗」，
碰到了就必须有明确答案，**不许「应该没事」**。

## 一、边界与异常（最高频事故源）
- 空值：入参为 None / 空串 / 空列表 / 空对象时，每一层调用会怎样？
  dict 取键、列表取 [0]、`a.b.c` 属性链是最常见的崩点。
- 数值边界：0、负数、极大值、小数精度（金额与计数一律避免 float 裸算的累计误差）。
- 超长与超量：超长字符串、上千条的批量输入、没做分页的全量查询。
- 异常处理红线：**禁止裸 `except: pass` 吞异常**——要么处理（记日志 + 降级/重试），
  要么让它炸出来。吞掉的异常等于把今天的报错换成下周的灵异故障。
- 失败路径：主流程成功不算完，逐问「每一步失败后，状态是否仍然一致」——
  写了一半的文件、扣了款没发货的订单、删了源没删索引。

## 二、资源与并发
- 打开的文件 / 连接 / 锁，在**所有**退出路径上都关闭了吗（含异常路径）？
  用 with / try-finally / defer 这类语言级保证，不靠「记得 close」。
- 循环内不做 IO / 网络 / 建连接（N+1 模式）；能批量就批量。
- 并发共享状态：全局变量、模块级缓存、多线程写同一文件——有锁吗？锁的粒度
  会不会死锁？**单测通过不代表并发安全**，并发问题要靠设计保证而不是靠运气。
- 幂等性：重试、重复请求、消息重复消费时，同一操作执行两次结果必须不变
  （尤其支付、发送、计数类操作）。

## 三、安全（每次改动都扫一眼）
- 拼 SQL / 拼命令 / 拼 HTML = 注入。参数化或转义，没有例外。
- 路径拼接必须校验：用户可控输入参与拼路径时防目录穿越（先 resolve 再判前缀，
  或白名单校验文件名）。
- 密钥与令牌不硬编码、不打日志；日志里的手机号 / 身份证 / 邮箱脱敏。
- 对外接口：入参校验（类型 / 长度 / 范围）；错误信息不回显内部堆栈与路径。
- 新增依赖必须来源可信、版本锁定；升级依赖后过一眼 changelog 的破坏性变更。

## 四、兼容与可回退
- 跨平台：路径分隔符（用语言自带的路由 API，不手拼 `/` 或 `\`）、文件编码
  （Windows 默认 GBK，读写文件显式 UTF-8）、换行符、文件名大小写敏感差异。
- 数据兼容：改字段名 / 改格式时，旧数据还读得动吗？迁移脚本在哪、可重跑吗？
- 接口兼容：改出参、删字段之前，确认所有调用方（前端、脚本、第三方）已同步修改。
- 可回退：这次改动出问题，怎么回到上一版本？配置开关、灰度、revert 方案，
  动手前至少想清楚一个并写进提交说明。

## 五、提测前过单（逐项打勾，全绿才提交评审）
- [ ] 空值 / 边界入参各试过一次：不崩、行为合理
- [ ] 无裸吞异常；所有异常路径上资源正确释放
- [ ] 无循环内 IO；并发路径有并发保护或明确论证过只在单线程运行
- [ ] 无拼接 SQL / 命令；无硬编码密钥；日志无敏感明文
- [ ] 路径 / 编码 / 换行已跨平台处理（Windows 环境必查）
- [ ] 已想好并写下回退方式（revert / 开关 / 迁移脚本）
- [ ] 新增或修改的逻辑有对应测试，改动的测试全部通过
