# 周报 / 晨报生成器守则（市场包）

适用：为个人或团队生成晨报（昨日 / 今日 / 阻塞）与周报（本周 / 风险 / 下周）。
第一原则：**先取材，再总结，不许凭印象编**。事实原料来自任务系统、运行记录、
提交历史与日志；生成器的工作是把原料提炼成「能支撑决策」的信息，不是文学创作。

## 一、取材清单（动笔前先收集）
- 已完成：本周关闭的任务、成功结束的运行、合并的提交 / PR（git log --since 起止）。
- 进行中：各任务当前状态、最近一次运行结论、卡在哪一步。
- 信号类：评审打分、测试通过率、失败与重试次数、耗时的环比变化——量化的来源。
- 未进系统的口头承诺 / 临时插活：单独列出并标注「口头事项」，不混进正式条目。

## 二、晨报结构（10 行以内，站着读完）
- **昨日完成**：2-4 条，每条写一个**结果**（不是动作）。
- **今日计划**：2-4 条，每条可验证（「提测搜索分页」，而不是「继续做搜索」）。
- **阻塞**：0-2 条，每条带「需要谁 / 需要什么」；没有就写「无」，不硬凑。

## 三、周报结构
1. **本周一句话**：本周最重要的结果或结论。上级只读这一行也能掌握大局。
2. **关键进展**：按目标 / 项目分组，每组 1-3 条；每条 = 结果 + 量化 + 对照计划
   （提前 / 按期 / 延期几天）。流水账禁止——「周一做了 A，周二做了 B」是日志，
   不是汇报。
3. **风险与阻塞**：每条 = 风险描述 + 影响面 + 需要的支持或缓解方案。
   **只报风险不给方案 = 把问题原样上交；报喜不报忧 = 把雷埋到下周。**
4. **下周计划**：2-5 条可验证的目标，与风险呼应，高风险项排前面。

## 四、写作纪律
- **量化**：能带数字必带数字（章数、字数、通过率、耗时、条数）；
  「大量」「明显」「基本完成」这类模糊词出现即重写。
- **结果导向**：写「完成了 X，达到 Y」；「在做 X」「推进中」放进计划或阻塞，不进步进展。
- **动词开头、一条一意**：每条脱离上下文独立可懂。
- **诚实纪律**：延期就写延期，附原因与新预计时间；数据缺失标注「缺」，不估算充数。
- **篇幅纪律**：周报正文 ≤400 字（附录与链接不计）；超了说明没提炼。

## 五、常见毛病对照（反例 → 正例）
- 反例：「本周推进了 A 项目。」→ 正例：「A 项目完成搜索分页改造并提测，1 万条数据下翻页响应小于 200ms。」
- 反例：「一切顺利。」→ 正例：「整体按期；联调依赖的 B 接口周三可用，已与对方确认。」
- 反例：「风险：时间紧。」→ 正例：「风险：评审通过率低于阈值会触发返工，预计延期 2 天；已加排一轮预审。」
- 反例：把 12 条流水账逐日列出 → 正例：归并成 3 条按目标分组的结果，逐日明细放附录链接。

## 六、周报模板（可直接复制）
```
# 周报（MM.DD - MM.DD）

一句话：完成xxx，指标y环比+z%；主要风险：xxx。

## 关键进展
- 【目标A】交付xxx（量化数据）；对照计划：按期 / 延期n天
- 【目标B】……

## 风险与阻塞
- 风险：……；影响：……；需要：……（或已采取措施：……）

## 下周计划
- ……
```

## 七、自检
- [ ] 每个数字都能在任务 / 运行记录 / git log 里找到出处
- [ ] 无「继续推进」「持续优化」这类无信息量条目
- [ ] 风险条目全部带缓解方案或明确的求助对象
- [ ] 下周计划每条都有可验证的完成标志
