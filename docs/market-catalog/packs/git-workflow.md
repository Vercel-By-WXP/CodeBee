# Git 提交与分支守则（市场包）

适用：任何带版本控制的工程或写作任务。目标只有一个——**让半年后的自己（和协作者）
能从提交历史里读懂「为什么改」，并且任何时候都敢放心回滚**。本包约束的是纪律，
不是 git 教程；每条红线背后都是一类真实发生过的事故。

## 一、提交信息（Commit Message）
- 格式：`类型(范围): 一句话摘要`。类型闭集：feat / fix / docs / refactor / test / chore，
  不自创类型（update、modify、change 这类词无法被工具统计与检索）。
- 摘要 ≤50 字，祈使句，结尾不加句号；写「做了什么」，不写「改了哪些文件」。
  反例：`修改了一些文件`；正例：`fix(api): 空请求体导致 500 的问题`。
- 摘要说不清的改动，空一行后写 body：解释**为什么改**（背景、权衡、副作用），
  不要复述 diff 本身能看出来的「改了什么」。
- 一次提交只做一件事：修 bug 的提交里不顺手重构；发现顺手该改的，另起提交。
  混合提交无法单独回滚，是最常见的 git 事故根源。

## 二、分支模型
- `main`（或 master）永远可发布：只接受经过验证的合并，禁止把未验证的功能代码
  直接 push 上去。
- 分支命名能看出目的：功能 `feat/<短横线描述>`，修复 `fix/<短横线描述>`；
  一个分支只对应一个目的，合完即删——活过两周的分支几乎必然产生严重冲突。
- 同步纪律：动手前先拉最新主干；分支生命周期超过 2 天，每天至少同步一次主干，
  冲突在自己分支上解决，不把冲突攒到合并时刻。

## 三、危险操作红线
- 禁止对**已推送的公共分支**做 `reset` / `amend` / force push——重写历史会让所有
  协作者的本地仓库错乱。公共分支上的错误用 `git revert` 生成反向提交。
- `git push --force` 只允许推自己的功能分支；确需覆盖时用 `--force-with-lease`
  （远端有别人新提交时会拒绝，防误伤）。
- 提交前不许 `git add -A` 了事：先 `git status` + `git diff --staged` 逐块确认，
  防止把临时脚本、日志、密钥、二进制大文件带进历史（进了历史几乎删不干净）。
- 敏感信息（密钥、口令、内网地址）一旦提交，**立即视为已泄露**：先作废并轮换凭据，
  再清理历史，顺序不能反——清理历史赶不上爬虫抓取的速度。

## 四、冲突与回滚
- 冲突解决以**业务正确**为准，不以「保留谁写的」为准；解决完必须编译/跑测通过
  再提交，冲突盲选是隐性 bug 的最大来源。
- 回滚决策树：未推送 → `reset`（本地随意）；已推送未发布 → `revert` 反向提交；
  已发布出问题 → 先 revert 恢复线上，再慢慢定位，**不在主干上现场调试**。
- 大改动合并前先试合：`git merge --no-commit --no-ff` 预览，或在临时分支上合一遍。

## 五、提交前自检清单
- [ ] `git status` 干净：没有预期外的未跟踪/被修改文件
- [ ] `git diff --staged` 逐块看过：无调试代码、无密钥、无大文件
- [ ] 提交信息符合 `类型(范围): 摘要`，摘要 ≤50 字且脱离上下文能看懂
- [ ] 一次提交一个意图；无关改动已拆分
- [ ] 功能分支基于最新主干；公共分支未被重写历史
- [ ] 提交后本地测试/CI 通过；红了立即 fix 或 revert，不留红主干
