# 统一执行与评测标准

本文规定 CLI、供应商、模型、协议和完整任务的评测边界，以及所有执行入口复用的失败分类与换路原则。目标是让“能连通”“模型能回答”和“任务通过验收”成为不同且可核对的结论，避免低层检查的绿灯冒充端到端成功。

本文主干治理的是失败发生后的分类、止损、换路和记账；配套的"预防性预检""并行协作与发布纪律""根因修复闭环"三节把一部分防线前置到启动、排程与发布环节，"内容质量判定门"一节给出成品质量的判定口径与裁定权归属，"候选打分权重表"一节把选路侧的分值口径收成唯一出处。但它仍不能替代供应商供给、密钥余额、链路配置的实际管理，因此不能单独承诺降低原始失败率。失败率要靠至少一家健康异上游、可用余额和持续观测共同改善。

## 评测层级

| 层级 | 验证内容 | 通过条件 | 不能据此推断 |
|---|---|---|---|
| CLI 安装与默认配置 | 可执行文件、版本、本机登录态和默认端点 | CLI 冒烟在有限超时内返回独立一行 `OK` | 用户绑定的供应商或任务模型可用 |
| 供应商可达性 | 地址可达、`/models` 是否提供模型目录 | 返回可解析模型列表；若端点明确不支持列表，只记“可达、密钥未验证” | API 凭据有效、模型可生成 |
| 协议适配 | OpenAI、Anthropic 等请求形状与该协议响应结构 | 最小请求得到符合协议结构、无错误字段的响应 | 指定模型有权限或有额度 |
| 模型可用性 | 指定供应商、模型、协议和 KEY 的最小真实生成 | 返回非错误响应结构，含模型结果，且实服模型与请求模型一致；若网关返回实服模型，漂移必须单独记为失败或告警 | 长上下文、工具调用或任务质量达标 |
| 多模态能力 | `image_in` 图像输入、图像输出及其协议子路径 | 按任务声明分别完成图像输入和/或输出探测；输入有视觉语义回执，输出有可解码且符合约束的图像构件；HTTP 200 但含错误信封仍算失败 | 文本 chat 通过、模型名含 `vision` 或 UI 开启 `image_in` 就能证明图像能力 |
| 绑定路由 | `bind_agent` 实际展开出的首选和后备链 | 每次尝试保留生效的供应商、模型、协议、KEY 身份；失效时按规则换路 | CLI 默认冒烟可替代绑定路由测试 |
| 完整任务 | 真实任务管线、确定性验证、独立评审与终态收口 | 验证命令通过且质量门通过；评审器错误单独记失败，不能算质量不通过 | 单次模型连通测试等于任务成功 |

评测结果统一保留 `passed`、`reachable`、`reachable_unverified`、`failed` 四种基础语义；当带时钟的证据过期或被健康事件作废时，读取层返回 `stale`（同时 `fresh=false`、`ok=false`），它不是新的成功态。`reachable` 表示供应商的模型目录请求成功，`reachable_unverified` 表示端点可达但不支持模型目录、密钥尚未验证，`passed` 表示指定模型已完成最小生成测试。兼容旧 UI 的 `ok` 字段可以保留，但前两种可达状态不能显示成模型已验证可用。

`passed` 是带时钟的证据，不是永久能力声明。每条供应商/模型评测必须记录 `evaluated_at`、`expires_at` 和 `fresh`；默认保质期为 24 小时，可用 `TUTTI_EVALUATION_TTL_S` 调整。供应商健康事件失败时立即使该上游的相关结论失效；探针恢复只能恢复健康状态，不能复活旧的 `passed`，必须重新完成评测才能再次路由。

## 统一执行算法

1. **输入预检**：解析任务类型、角色、难度、超时预算、验证条件和取消状态；核对 CLI 存在、必需凭据存在、协议与 CLI 能力兼容、模型名不是占位符。绑定 CLI 时还要校验自家配置的托管段与当前绑定一致；指纹命中不能跳过文件哈希校验。
2. **确定路由**：显式绑定保持原顺序；未绑定才使用自动推荐。每个候选形成完整身份 `(CLI, normalized provider host, protocol, model, key_id)`。同一规范化 host 的别名、端口和路径变体按一个上游去重；同一模型与 KEY 的重复候选去重；不同 KEY 保持独立，因为它们有独立授权和额度。常用链必须至少保留一家异上游候选。
3. **按统一失败码处置**：取消立即终止，且取消产生的杀进程、断管道和尾部错误不得进入 KEY 冷却或健康惩罚——豁免判定以结构化取消标记（`raw.cancelled` / 结果 `cancelled` / `error_code=CANCELLED`）为准，不得靠错误文案匹配：CLI 取消串形如「取消；stderr/stdout: <被杀进程尾部>」，尾部含 429、欠费或无效 KEY 字样时文案匹配会把健康 KEY 打进 30 分钟冷却、把一次用户点击记成供应商故障。缺少凭据或认证失败只尝试已配置的备用 KEY；403 跳过同一上游的其他模型并试不同上游；余额/配额切备用 KEY 后再换供应商；429 做一次有 deadline 上限的等待，再按后备链尝试；网络、断流、服务端 5xx、瞬态本地锁和超时按有限预算换模型或上游；解析、输入、协议配置等不可恢复错误停止并给出明确修复指引。相同错误签名连续命中达到阈值时，终止标记必须穿透所有外层重试和换将循环。
4. **共享预算并记录尝试**：所有候选共享一个单步截止时间和有上限的尝试数。每项记录 CLI、供应商 ID、规范化上游、模型、协议、KEY ID、耗时、token 分项与成本、错误码和是否跳过；绝不记录密钥值或任务正文。默认单步预算以 `runner.DEFAULT_TIMEOUT`（1200 秒）和 catalog 的 `orch.timeout_ms` 为准；连载长步骤的 2400 秒预算必须在流程代码中显式标注，不能默认为所有步骤延长。
5. **验证实际结果**：响应必须有正确协议结构且无 `error` envelope；进程退出码为 0 仍必须解析错误事件、错误信封和结果内容；需要工具的步骤还必须有 `command_execution`、`file_change` 或 `mcp_tool_call` 等实际动作证据。完整任务按确定性验证和质量门判定。取消保持取消，配置/评测失败与任务质量失败分开呈现。

## 多模态评测规则

多模态是独立能力维度，不能从文本 chat、模型名称、供应商目录或 UI 徽章推断。任务在进入路由前声明所需能力：`image_in`（图像输入）、`image_out`（图像输出），二者可以同时要求，也可以只要求其一。候选必须逐项满足声明；只通过文本路径的候选只能记为文本 `passed`，不能被选来执行视觉任务。

1. **输入探测**：对声明 `image_in` 的候选，用隔离的确定性小图（不含用户内容）和固定问题走该协议的真实图像分支。OpenAI/Anthropic 等协议要分别验证 image part 的字段、媒体类型和编码，而不是把图片路径拼进文本。回答必须包含对图中已知标记的可核对视觉语义；仅返回通用礼貌语或忽略图片，不算通过。`image_in=true` 是路由提示，缺省或仅由模型名推断时仍要实测；探测失败应回写“未验证/不支持”，不得静默把图片交给纯文本模型。
2. **输出探测**：对声明 `image_out` 的候选，用固定短提示请求最小图像构件。验收同时检查响应无错误信封、媒体类型和字节可解码、尺寸/格式满足任务约束，并确认构件已落到本次 run 的归属路径。URL、base64 或 JSON 外壳都只是传输形式；没有实际图像字节、无法解码或只返回文本描述，均为失败。`image_in` 通过不能推断 `image_out` 通过，反之亦然。
3. **HTTP 200 仍先判信封**：在读取任何 `content`、`data`、URL 或 base64 前，递归检查响应顶层和协议定义的嵌套对象是否含 `error`、`errors`、`status=failed`、`finish_reason=error` 等失败信号。HTTP 200 + 错误信封、空 choices、缺图像字段、错误字段与结果并存时统一记 `VENDOR_ERROR`（有明确 401/403/402/429/5xx 则使用对应码），不能记 `passed`，也不能以退出码 0 覆盖。
4. **降级与记账**：没有 `image_in` 的候选只能走明确的文本降级，并在结果中标记图片未被模型看到；需要视觉语义的任务不得把该降级当成功。每次探测记录 `modality`、请求/实服模型、输入输出协议分支、构件摘要和错误码，不记录图片原文、base64、任务正文或密钥。图像能力结论和文本能力结论分别进入 TTL/健康时钟，任一能力失效都只熔断对应维度并触发异上游候选。

**实施边界**：当前运行时代码已接入 `image_in` 的请求形状和候选筛选；`image_out` 的真实生成探测、构件解码验收和按模态独立账本尚未接入。在这些闸门落地前，任何候选都不得仅凭文本通过或模型名推断为 `image_out` 已验证；健康失效按已实现的 provider/model 粒度熔断。

## 统一错误分类与换路矩阵

| 错误类 | 典型信号 | 动作 |
|---|---|---|
| `MISSING_CREDENTIAL` / `AUTH` | 缺 API Key、401、invalid key | 尝试同供应商启用的备用 KEY；都失败后报告密钥配置问题，不把 403 混成 KEY 错。取消路径不记 KEY 冷却 |
| `FORBIDDEN` | 403、forbidden、模型/账号无权限 | 同一上游不重复撞其他模型，转到不同上游；无异上游则返回权限诊断 |
| `QUOTA` | 402、余额或额度不足 | 冷却失败 KEY，尝试备用 KEY 和不同供应商；不对耗尽额度做原地重试 |
| `RATE_LIMIT` | 429、rate limit、too many requests、concurrent limit、并发超限 | 冷却/切 KEY；只在截止时间允许时等待一次，再继续后备候选 |
| `UPSTREAM_SERVER` | Unexpected server error、5xx、overloaded | 有界重试或切换其他模型/上游；同上游失败后不把更换 CLI 名称当成新上游 |
| `NETWORK` | stream disconnect、连接重置、DNS/连接失败 | 尽早停止卡住的 CLI 进程，杀全进程树（含孙进程）并关闭管道读线程，再切换候选；同上游不重复消耗整段超时 |
| `LOCAL_STATE` | CLI SQLite/database locked | 按瞬态本地冲突记录并有限换 CLI/重试；不要归因给模型质量 |
| `TIMEOUT` | 任务 deadline、CLI 超时、无输出停滞 | 使用共享 deadline 换较快候选；预算耗尽后终止，不能无限延长 |
| `MAX_TOKENS` | 思考占满 `max_tokens`，有思考心跳但无正文 | 与 `EMPTY` 分开；内置模型同轮只提额一次（8000→16000），仍无正文才终态；普通 CLI 只有拿到结构化信号时才能分类 |
| `CONTEXT_OVERFLOW` | 上下文超过模型容量、触发压缩 | 先压缩并确认 surface generation 前进，再重试一次；没有压缩进展不得重复发送原上下文 |
| `VENDOR_REFUSAL` | 内容策略拒答，或要求工具却零动作 | 先检查提示词是否含未脱敏凭据等自伤信号；若是自伤先修输入，不盲目换上游；否则作为上游结果处理，可试异上游，保留用户输入本身 |
| `PARSE_FAIL` / `EMPTY` | 输出结构错误、没有模型内容 | 协议探测/模型评测判失败；完整任务中不伪装成质量评审不通过 |
| `ENV_BLOCK` | CLI 缺失、路径/策略/本地运行时问题、重复守卫终止 | 给出本机修复说明；不通过换模型掩盖配置问题。重复守卫标记必须让外层流程立即收口 |
| `SIGNAL_IGNORED` | 发出终止信号后进程树仍存活或管道无法收口 | 记为本机终态，禁止继续重试同一进程；保留杀树和管道收尾诊断 |
| `CANCELLED` | 用户主动取消 | 立即结束，绝不降级或自动重试；不写入 KEY 冷却和供应商健康失败 |
| `VENDOR_ERROR` | 未能可靠归因的厂商/CLI 失败 | 保留通用错误码和本机详情；只有有明确证据时才提升为认证、配额或网络错误 |

错误文本分类只用来补充结构化进程状态；`cancelled`、`timed_out` 和显式 HTTP 状态优先。未能识别的厂商错误保留为 `VENDOR_ERROR`，不能猜成配额或认证失败。

## 成本与时延预算

token 用量和耗时是独立于"成/败"的第三条轴：一次 `done` 可以烧掉三倍 token 或吃满整段超时预算，一次 `TIMEOUT` 也可能只输在候选延迟上。本节约定**怎么计量**和**闸门在哪个口径上判**，不承诺省钱——省了多少要先能在台账里指出来。优化手段（会话复用、前缀排序、级联分流）的方案与 ROI 见 `docs/migration/07-token-cost.md`，本节只定验收口径。

1. **每次真实调用必须入账**：走 `usage.record` 单一落账口，字段为 `input`/`output`/`cached`/`reasoning`/`total` 五个 token 分项 + `duration_s` + `cost_usd`，压缩净省另记 `saved`（零值不落字段）。内置直连、CLI 规划、书名简介、连通测试等旁路调用都要过同一入口；漏一条就是台账上的黑洞，不允许"这次先不入账"。`record` 内部吞掉一切异常——统计永远不能拖垮业务调用方。
2. **`cached` 不计入压力，但要计入了账**：压力口径 `token_meter.used()` = `input + output + reasoning`，**不含 `cached`**（缓存读不占新一轮上下文，也不按全价付钱）；`total` 含 `cached`，回答"这次花了多少"。两个量纲不得互换，也不得拿 `total` 去比模型容量。缓存命中率（`cached / (input + cached)`）是成本侧的验收指标，低命中是架构问题，不是厂商定价问题。
3. **事前预检与响应式熔断是两套量纲**：判断"本步会不会被拒"用 `token_meter.last_context()`（最近一次上下文体量）比**本步绑定模型**的容量，换将切到小窗口模型时先压缩再发；判断"这个 run 已用多少"用 `used()` 窗口累计（多次叠加、系统性偏大）。压缩触发阈值默认 0.8（`orchestrator.compaction.pressure_threshold` 可覆盖），推演类增强在压力比 >0.7 时先让位给正文章稿。容量按 `token_meter` 表查，未命中用 128000 兜底，`data/model_capacity.json` 热改即生效——兜底值不得当成真实容量用来声称省钱。
4. **token 预算闸只拦"下一步"**：`budget.max_tokens_per_run`（默认 0=不限）达到后阻断后续真实调用并判 `ENV_BLOCK`，越过线的当前步允许完成，续跑可在用户调高预算后接手。预算熔断是运维开关，**不得记成模型质量失败，也不得计入厂商归因**；把它当质量红灯用等于把配置问题伪装成模型问题。
5. **耗时与均价只作软加减分**：在线信号取自 `usage.routing_stats`（成功率按 Beta(3,1) 平滑、`p95_duration_s`、`avg_cost_usd`）。P95 延迟惩罚上限 -18、成本惩罚 -4，与 CLI 静态能力差同量级，保证真实延迟足以改变自动选择但不推翻能力结论；样本为 0 时该项记 0，不得凭猜测压低或抬高候选。精确维度样本不足时按 任务+角色 → 任务 → 全局 逐级回退，回退层必须出现在候选理由里。静态分项（能力基线、绑定、历史、亲和度、配额、档位、价格）的取值同受本条纪律约束，统一见「候选打分权重表」。
6. **开跑前预估用于排程，不用于验收，也不做进队阻断**：`usage.estimate` 按同类任务的历史 run 加总给出 token/美元/耗时的中位数、均值与 P90，`duration_source` 必须区分 `history` 与 `baseline`；无历史样本时的保守基线不得显示成实测数据，估出来的耗时只用来设超时预算和排先后，不构成任务通过条件。样本口径：`samples < 10` 或 `duration_source=baseline` 即视为薄样本，UI 必须点名「按流程基线估算」，不得把薄样本读数当实测承诺。**定案：这一层不设进队/开跑阻断**——类型级预估切不开同类型内的成本尾部（实测 serial_novel 中位 12.1 万 / P90 185 万 tok，15 倍；code 114 倍），否决切不开「正常长任务」与「跑飞」，误杀面正好落在前者；阻断只由 `budget.max_tokens_per_run` 在真实累计用量越线时判（`_spawn_step` 只拦下一步，当前步允许完成）。定案改做的是事后对账：run 由非终态翻进终态那一次，把 `create_run` 落的预估快照（优先 P90，含 `estimate_source`/`estimate_samples`）与本次真实 token/耗时合计逐条比对，写 `usage/estimate-audit-YYYYMM.jsonl`（含 `ratio`/`over_p90`/`est_basis`），只回看窗口内快照、绝不回读当前台账以免本次消耗自我膨胀；比值攒够窗口后才用于评估阈值要不要收紧。
7. **首字延迟与吞吐只入账、不进口径**：`usage.record` 带 `first_token_ms`（请求发出 → 第一个**带内容**的增量：思考 / 正文 / 工具参数任一）与 `tokens_per_sec`（该次 output token ÷ 首末内容增量窗口）。零值不落字段——「缺字段」表示不可测，不能读成「首字 0 毫秒」；汇总只对可测样本求均值与 P95，`perf_samples=0` 时用量页显示「暂无可测数据」。只有内置直连的流式路径测得到，CLI 事件流没有逐 token 时刻、非流式回落同理。二者尚未进入路由加减分与任何验收闸。不得用「总耗时」替代「响应快慢」下结论——长正文任务的总耗时主要由输出量决定，与候选是否灵敏是两件事。
8. **不得据以推断**：token 消耗低不代表质量高，耗时短不代表链路健康。成本或时延的改善必须按"根因修复闭环"第 4 步给出前后差异（同类任务的 `avg_tokens`/`avg_cost_usd`/`p95_duration_s`），单点跑得快慢不构成结论。

## 候选打分权重表

「成本与时延预算」第 5 条只成文了在线信号一类软加减分，本节把其余分项一次性落成唯一出处。**分值表治理的是排序，不是结论**：任何分项都不得越过「评测层级表」声称"能力已验证"。被打分对象只有两类——CLI（智能体）与模型链；厂商不在其中。

### 打分前置：硬约束不进分数

评分前先过滤，过滤结果不参与加分、也不可被高分豁免：协议匹配、CLI 启停、供应商健康状态、密钥可用、评测结论新鲜（`passed` 未过期且未被健康事件作废）。

**厂商与供应商不打分**，只走状态口径：`passed / reachable / reachable_unverified / failed / stale` 加 TTL 与熔断（`ok → failing → down → recovered`）。把厂商折成一个分数，等于允许"其他项很高"来掩盖它已经 down，这与「评测层级表」把各层结论分开的初衷相反。厂商的真实表现只能透过 provider+model 维度的在线统计间接进入模型链分数。

分数排定后仍有一类**硬规则可否决排序**，不得降格为加减分项：评审者必须与实现者跨 CLI 家族，同族池为空才回退且必须在理由里如实标注回退；换将时与失败上游同 host 的候选延后让位，403 明确拒绝的上游始终剔除、异上游耗尽也不捡回；自动内容评审只取综合分前两名（`AUTO_CRITIC_LIMIT`）。

### CLI 候选分

总分 = 能力基线 + 绑定链 + 历史战绩 + 能力亲和度 + 在线信号 + 配额惩罚，理由字符串必须逐项回显分值。

| 分项 | 取值 | 口径与限制 |
|---|---|---|
| 能力基线 | codex/claude 84、opencode 74、qwen 72、aider 70、openclaw 60、generic 55、mock 10，未知 kind 60 | 人工先验，不是实测。只用于无样本时区分候选，不得据以声称某 CLI 质量更高 |
| 绑定链 | ≥2 条 +8、单条 0、空链 -25 | 单条只拿 0：单点无降级空间，给 +8 是信号失真。任务画像/自动分发模式下空链记 0 不扣 25，因为该模式会自行展开供应商链，扣分等于惩罚用户未做手工绑定 |
| 历史战绩 | `18×胜率 + min(6, 次数) − 24×(1−胜率)×min(1, 次数/3)`，无记录 0 | 实际区间约 -21…+24。前 3 次线性加权：既防一次偶发失败埋没新面孔，也防 0/3 全败还拿经验分排在未跑过者之前 |
| 能力亲和度 | 维度取 writing/coding/reasoning/vision（`dispatch.task_dimension` 归一），维度×CLI 查表 0…10；`review` 角色再 +4(claude)/+3(codex)/+2(qwen) | 只在任务画像启用（`_dispatch_task_type`/`dispatch_enabled`）时生效，旧调用走兼容模式恒为 0。只加分不设罚，不得用它覆盖健康与历史信号 |
| 在线信号 | 成功率 ±8、P95 延迟 ≤-18、均价 ≤-4 | 口径、平滑与回退层要求见「成本与时延预算」第 5 条 |
| 配额惩罚 | `-45 × min(1, 本小时 token / 配额)`，未配配额为 0 | 封顶 -45 足以盖过历史加分。这是运维开关信号，**不得记成模型质量失败**，口径同预算熔断 |

### 模型链候选分

| 分项 | 取值 | 口径与限制 |
|---|---|---|
| 质量（由 priority 折算） | `max(-8, 20 − (priority−1)×4)`，未标 priority 记 0；再按难度缩放 easy ×0.25、default ×0.65、hard ×1.0 | 缩放的意义是让便宜档在低风险任务上真的能压过旗舰，而不是名义上兼顾成本。**priority 是供应商模型列表里的排位**（用户手工排序 + 入库时的名字启发式估分），不是能力实测，所以这项分值只能读成"用户把它排在第几"，不得拿来充当质量结论 |
| 档位 | easy：budget +18 / standard +8 / premium -6；default：budget +2 / standard +6 / premium +5；hard：budget -8 / standard +4 / premium +12 | tier 缺失按 standard，模型级优先于供应商级。重排只在 easy/hard（或调用方 `force`）发生，**default 难度必须保持用户配置的原始顺序** |
| 价格 | `-min(18, log10(in + 2×out + 1) × (7.0 若 easy 否则 2.0))` | 输出按 2 倍权重（更贵且更决定整步成本）。价目缺失记 0 并标注"价格未知"，不得猜价 |
| 能力命中 | 供应商 `strengths` 含本次维度 +10，否则 0 | 供应商自述标签，软信号；能力结论仍由「评测层级表」各层实测给出 |
| 视觉 | 声明 `image_in` 的维度：真 +24、假 -24；其他维度 0 | 全表最大单项，因为把图交给纯文本模型是错答而非劣答。声明不作数，以实测评测为准（见「多模态评测规则」） |
| 在线信号 | 成功率 ±6、P95 ≤-12、均价 ≤-3 | 按 provider+model 维度查，同一套平滑与回退层口径 |

自动推荐链在此排序后取前 `MAX_CHAIN_ATTEMPTS`（8，按模型×KEY 展开计）；候选阶段不得先截前三条——便宜档常排在供应商列表尾部，截断等于让成本评分看不到真实备选。显式绑定链的重排需绑定级 `difficulty_routing` 或全局 `cascade.enabled` 打开才做。

### 调参纪律

1. 改动本节任一数值必须在同一提交内更新本表，并保留理由字符串里的分项回显——理由是这套权重的唯一可观测面，不得为省字裁掉。`test_candidate_scoring_standard.py` 把本表数值与代码常量逐格比对，任一侧漂移即红在 CI；它只保证两边一致，不判断新值是否更好。
2. 权重变更要给出前后差异证据（同类任务的自动选路结果或候选排序变化），"感觉更顺"不构成理由，口径同「根因修复闭环」第 4 步。
3. 新增分项必须先回答它能否被硬约束否决：不可否决的写进上面的硬规则段，不得做成加分项。
4. 能力基线与亲和度表是 2026-09 的人工先验。台账样本足以取代时应改为从 `usage.routing_stats` 派生，并在本节记录替换结果与原因，不得只删文档留码，也不得只改码留表。

## 实施约束

- 自动推荐只在完全没有显式绑定时启用。显式链全失效必须报错，不得静默使用 CLI 本机默认供应商。
- `test_provider`、`test_model`、wire probe、CLI 默认冒烟、绑定路由和完整任务各自产生独立结果，不共享“成功”标签。
- 2xx 不等于生成成功：含 `error` 的 JSON、错误字段缺失、协议响应无模型结果都算失败。
- exit 0 不等于生成成功：Codex 等结构化事件流要检查 `turn.failed`/`error`；通用 CLI 必须检查错误信封、空结果和任务要求的实际动作，适配器不能只看退出码。
- 模型可用性要记录请求模型、实服模型和漂移原因。`served_models` 已接入 Claude 解析路径；没有实服信息时只能记“未验证”，不能默认为一致。
- `repeat_guard` 当前按 `(run_id, role, prompt fingerprint)` 统计连续调用，3 次提醒、5 次停止；它是提示重复守门，不等同于全链路错误签名熔断器。跨候选同因止损仍需由外层路由统一传递终态标记。
- CLI 自家配置同步属于运行前防线。同步失败不能静默变成“预检通过”；发布版本必须确认运行中的副本已包含该防线，否则标准没有生效。
- 测试和评测必须隔离真实用户配置：使用临时数据目录、假 HOME 或等效隔离，并启用 `tmp_data_no_home_write` 防止 settings/config 被夹具污染真实家目录。评测不得把真实密钥、任务正文或原始 stdout/stderr 写入持久台账。
- 任务成果的确定性验证还要检查内容编码和乱码墙。文件存在、命令退出 0、字数达标都不能证明中文内容可读；发现 `U+FFFD` 墙或明显错码时应判验证失败并给出编码修复提示。
- 终态写入使用单一 CAS 规则：`queued/running` 才能翻转到 `done/failed/cancelled/timeout`，迟到异步写手必须被拒绝；终态后的步骤统一收口，不能复活任务。
- 新增重试/换路必须测取消、deadline、相同 host 去重、备用 KEY、不同上游后备和终态保护。
- 错误台账只持久化分类后的简短原因、实际路由身份和非敏感元数据；原始 stdout/stderr 和任务内容只留在本机运行详情。

| 成本与时延计量 | `usage.record` 已落 token 五分项（含 `cached`/`reasoning`）与 `duration_s`/`cost_usd`/`saved`，启动 `backfill_from_runs` 幂等回填；`token_meter` 提供 `used`/`last_context`/`pressure_ratio`/`capacity`，`budget.max_tokens_per_run` 熔断与 `usage.estimate` 已接线，路由按 `p95_duration_s`/`avg_cost_usd` 软加减分且候选理由带样本层（`fallback` 标签），换将 `attempt_history` 逐项带 `key_id`/`protocol`/`tokens`/`usage` 分项/`cost_usd`，缓存命中率已进用量页 | 计量与闸门已落地；中间失败候选尚未逐条进用量台账（每步仍只落最终一条，逐尝试消耗只在 `attempt_history` 里）；TTFT 与 tokens/sec 已有计量字段（仅内置直连流式可测，缺字段=不可测），尚未进路由与验收口径，`estimate` 尚未成为排程前置闸，成本/时延的前后差异比对仍靠人工看用量页 |
| 候选打分权重 | `router.score`（基线/绑定/历史/亲和度/在线/配额）与 `dispatch.score_model_entry`（质量/档位/价格/能力/视觉/在线）已按本表取值实现，理由字符串逐项回显分值与样本层，`dispatch_decisions` 已产出脱敏排序明细；`test_candidate_scoring_standard.py` 把本表每个数值与代码常量钉在一起 | 分值与文档已对齐且有守卫；能力基线与亲和度仍是人工先验，未随真实台账校准，调权重时守卫只要求同步改表、不判断新值是否更优 |

## 配套运营闭环

标准上线前做一次供给盘点：为常用 CLI 和角色逐条列出当前链首、KEY 余额/有效期、规范化上游 host、异上游备选和最近一次真实生成时间及其耗时与 token 消耗（台账可直接取）。任何链缺少异上游、所有 KEY 余额未知或只有 `reachable_unverified` 时，不得把它标成“可生产”。

上线后连续观察两周新错误台账，按 `error_code`、规范化 host、模型、CLI 和任务角色统计。优先处理数量、耗时与 token 消耗最高的三个错误类（token 取自用量台账同 run/step 失败侧聚合，错误台账本身不存 token）；分类器对旧的 56 条弱详情不做猜测回填，也不因继续增加分类枚举而掩盖供给或配置问题。每次修复都要记录运行中的版本、是否已重启/发版，以及修复前后的同类错误率。

## 根因修复闭环

失败分类、止损和记账只处理现象，不等于根因收敛。每个 `error_code` 聚簇必须走完下面四步才算关闭，缺任一步不得记为"已处理"：

1. **定位到可复现证据**：给出触发该聚簇的最小复现或原始错误签名，不能只凭分类计数下结论。分类器无法归因的记录保留为 `VENDOR_ERROR`，不猜测升级。
2. **产出持久修复**：区分"真修复"与"自愈/绕过"。瞬态红测试自行转绿（如换将配额抖动）只能记为观察，不能作为关闭依据；关闭必须指向一处根因改动。
3. **落一条回归守卫**：为该聚簇新增或收紧一个自动化守卫（测试或扫描器），保证同类问题再出现时红在 CI 而非红在值班日志。守卫必须能在无并行噪声下单独复现该失败。
4. **量化前后差异**：记录运行版本、是否已重启/发版，以及修复前后同类错误率或同类红测试计数；涉及成本与时延的修复按「成本与时延预算」用同类任务的 `avg_tokens`/`avg_cost_usd`/`p95_duration_s` 给出前后差异；无差异证据不得声称已降低失败率或已省钱。

两周观察期内优先处理数量、耗时与 token 消耗最高的三个聚簇（token 口径同「配套运营闭环」），并按本节闭环逐个收口；继续增加分类枚举不视为闭环，也不得用来掩盖供给或配置问题。

## 预防性预检

分类只治事后，下面两类必须前置到启动与排程，避免整批任务未跑先废：

- **开机单例与端口**：服务启动前检查监听端口（如 8765）是否被本进程旧副本或他进程占用（`WinError 10048`）。端口冲突是重复启动/单例问题，判为 `ENV_BLOCK` 并给出本机清理与单例提示，不得记为供应商故障，也不得靠换模型掩盖。
- **自迭代调度预算**：调研采集与自动推荐须核对当日 KEY 余额与并发上限；配额满员或并发超限导致的组级瞬失败按 `QUOTA`/`RATE_LIMIT` 处理并顺延复扫，不做原地风暴重试，也不把这些瞬失败计入任务质量失败。

## 巡检自动化默认纪律

任何被反复人工执行的发版前巡检项，一旦第二次靠人肉发现，就必须固化为自动化守卫并入测试列，把"人肉巡检"降级为"守卫兜底 + 报告"。已知适用面包括：i18n 重复键/静默覆盖扫描、乱码墙与内容编码检查、终止信号后进程树存活检查、活计划勾选完整性（Stop gate）。守卫须零依赖真实用户配置（临时数据目录、假 HOME、`tmp_data_no_home_write`）。

## 发布与通知硬闸

发布不允许靠记忆执行。根目录 `npm run release:gate` 必须依次通过全量
`unittest discover`、发版前后两次 `git status --porcelain` 清洁检查、实际
`npm pack` 归档解包，以及从归档目录导入 `app.main` 和错误码模块的冒烟；任一
项失败都退出且不执行发布。`npm run release` 只是在同一闸门通过后追加
`npm publish`，不能把在制品、测试红灯或坏包带入注册表。

路由层把“同一候选集合全部失败”与单个供应商 down 分开记账。连续三轮（阈值可由
`TUTTI_FAILURE_NOTIFY_THRESHOLD` 调整）耗尽候选后，默认在 Windows 发原生 toast；
配置 `TUTTI_NOTIFY_SMTP_HOST` 与 `TUTTI_NOTIFY_EMAIL_TO` 后同时发 SMTP 邮件。
通知只携带 run/task/role、候选数、规范化错误码、provider/model 摘要，不携带密钥、
任务正文或原始输出；同一 run 去重、同一故障期只提醒一次，取消不触发，发送失败
只记结果而不改写任务终态。

## 并行会话协作纪律

多个代理会话共用同一工作树时，执行标准只保证单链正确，不保证并发正确。以下纪律补齐并发面：

| 风险 | 实案 | 纪律 |
|---|---|---|
| 版本号占位 | v0.1.62 被并行会话备好、0.1.63 顺延 | `package.json` 版本一旦入提交即占用；他人不抢发、不复用该号，发版权归备版方 |
| 共享序号资产撞号 | 班次编号三次撞号、CHANGELOG 未发布段并发追加 | 序号类资产（班次、版本、批号）取用前先看在途会话；撞号留空位不顺延覆盖 |
| 契约变更不同步 | `_binding_bonus` 改元组未适配旧断言、`_drain_streams` 破坏旧测试契约 | 改动函数签名/返回结构/进程契约时，同提交必须同步全部调用方与测试断言；全量红灯归属改动方当班修复 |
| 在制品卷入 | runner.py/pipeline.py 在飞时他人提交被牵连 | 暂存区有他人在制品只允许指名路径提交（或分 hunk：patch 过滤/pathspec，只提交自己那部分，原样保留他人暂存与工作区）；改前重读目标文件 |
| 并发发版死等 | 树不干净导致发版班班顺延（0.1.48 教训） | 有他人在制品时不发*工作树*版，改用 **HEAD worktree 发布法**：在目标提交建独立 worktree，从该 worktree 执行 `npm pack`/`publish`，使未提交在制品天然不入包；干跑与实际归档 shasum 必须一致以核对未夹带。`release_gate.py` 的 `require_clean` 是本地闸，不能当成"阻塞即放弃发版" |
| 发布生效可见 | 修复入代码但运行副本未含，标准未真正生效 | 发布版本必须确认运行中的副本已包含目标防线（错误码枚举、CLI 配置一致性防线），否则不得声称已修复 |
| 全量失败归因 | 全量 N 失败须逐条归属本班或并行波 | 失败不笼统记"并行在途"，逐条指明归属会话与文件；归属自己的立即修，归属并行的记录在案并跟踪收口 |

## 旁路通道分层评测

CLI/模型执行链之外的通道各自产生独立的分层结论，互不借用"成功"标签：

- **CDP 浏览器发布链**：连接（CDP 可达）→ 登录态（目标站会话有效）→ 表单填充（字段可见且值正确）→ 提交（提交闸通过、无弹层竞态残留）→ 发布后验证（URL/内容可回读）。任一层的绿灯不得冒充下一层；弹层竞态、url_any 带页面报错、submit 闸各自单独记失败。
- **外部系统读写链（禅道等）**：凭据与连通 → 数据形状校验 → 能力前置探测（如读图模型先看图能力，不会看图按降级链换将并落标记）→ 结果写回。读不到/形状不对留人工，不盲判、不阻塞主链（尽力而为语义必须在代码注释中显式标注）。
- **定时调度**：触发语义（interval 锚点不因手动触发/重启重算而漂移）→ 终态对账（last_status 必须回写终态，不停留 started）→ 中断补跑（服务恢复后对漏跑档期闭环）。每层有独立测试锚点。

## 数据资产入库守卫

结构化静态资产（i18n 字典、CHANGELOG、keywords、角色/流程清单等）的损坏不表现为执行失败，执行标准管不到；统一由守卫测试兜底：

- 新增或修改结构化资产时，同提交必须带或更新守卫测试：重复键、译值冲突、格式合法性、与词库/清单的同源性。
- 守卫测试进全量 `unittest discover` 例行跑，不是事后补丁；曾因实案修复补的守卫（如 i18n 重复键扫描）视同永久纪律，不得随重构删除。
- 资产损坏的修复只改数据不改语义；语义变更走正常评审，不借"修冲突"夹带。

## 内容质量判定门

执行链成功（进程退出 0、终态 `done`）不等于任务质量通过；质量不通过也不得降级成 `VENDOR_ERROR` 或 `PARSE_FAIL` 混进失败率统计。本节约定"什么算质量不通过"和"谁有权判"，与评测层级表里完整任务的通过条件对应。

### 判定口径

- **双闸相与**：`passed = 确定性验证通过 且 评审判过`。两闸各自独立出结论，任一不过即不过，不得用评审绿灯掩盖验证红灯。
- **阈值来源与分档**：`threshold` 默认 7.0；≥8.5 归 `hard`、≤6.0 归 `easy`，研究/方案/榜单类默认 `hard`（`task_compile._difficulty`）。难度只决定评审轮数、大纲要求和修复上限，低风险自动链可以减步骤，但**不能让没有确定性验证的任务跳过评审**。
- **逐维度全达标，不取平均**：任一评审维度均分低于阈值即判不过；分数缺失、阈值缺失、阈值非数值一律视为不达标（`_all_ge`），不做"猜成通过"的兜底。
- **章级与全局分离**：连载类阈值 ≥7.5 时单章阈值放宽 0.5 分，全局汇总仍按原阈值判定。这是量纲分离，不是绕过全局判定的通道。

### 评审器自身的失败

- 评审 CLI 报错、鉴权失败或无输出 → 记 `reviewer_error` 并进执行/评测面，**不落 0 分**，不写进质量统计。
- 评审 JSON 解析失败时先从原文抽取分数再判；只抽到分数、拿不到 issue 时不触发修复轮，避免把"格式错"当成"质量差"空耗修复预算。
- 反向硬约束：不得把"评不上"当成 0 分放行。运行时断言 `review_no_all_fail_zero` 拒绝"评审全 0 分却标 success"，`test_quality_gates.py` 锁住该行为。
- 所以"评审器错误单独记失败，不能算质量不通过"是双向的：既不能拿评审器失败冒充质量红灯，也不能拿它当作免检通行证。

### 明确判质量不通过（宁拒勿垃圾）

- **输入降级仍出成品**：大纲静默降级成空模板却按空模板写完、无大纲/无章稿/无圣经却生成作品信息。正确行为是中止并等自动续跑，不带病产出——废稿还会被续跑继承。
- **成品体裁错位**：报告腔简介（把研究素材当小说素材，简介写成 `# 网文选题分析报告…`）。判据是成品形态是否匹配任务体裁：推介文案面向读者，不得是报告标题、`#` 层级、列表符或 `**` 装饰。这类问题归质量门，不归执行失败。
- **内容不可读**：`U+FFFD` 墙与错码由确定性验证判失败（见实施约束），质量门沿用同一结论，不重复记账。

### 裁定权

只有评审维度集合（`rubric`，由任务或预置流程提供，上限 8 条）和确定性验证命令能给出 pass/fail。编排者、实现者和前端不得自行改写质量终态；质量红灯进质量台账与运行详情，不进错误分类枚举。新增质量维度必须同时指明该维度不通过时的呈现位置，否则不算可用判定。

## 选拔惩罚机制（设计稿，未实施）

「候选打分权重表」已含三类事后记账（历史战绩、在线信号、配额惩罚）与两类状态口径（KEY 冷却、供应商健康熔断），它们构成惩罚机制的主体——本节不再另造机制，只补齐四个缺口并立三条红线。**实施边界：本节为设计基准，落地前不改变任何现有分值与行为**；实施范围只挂编排链路（router/dispatch/换将），直连对话与手动指定场景不受管。

### 缺口一：记账粒度

历史战绩现按 CLI 全局记账；在线信号已有 任务+角色→任务→全局 回退层。统一收敛到 **(CLI, 模型, 规范化上游) × 任务类型 × 失败类别** 的最小记帐单位，失败类别沿用「统一错误分类与换路矩阵」错误码、不另立类目——拒答/超时/配额/流断是四种病，混记一锅会让降权信号失真（写小说强、跑代码弱的模型不该被代码失败拖死）。回退层沿用在线信号既有口径。

### 缺口二：上游家族传导

host 归一已用于换路（403 隔离、同 host 让位）与评测作废，但 KEY 冷却与败率惩罚仍以单 KEY/单 CLI 记帐。设计：**冷却与降权在规范化上游维度共享**——同 host 其余候选继承冷却并延后（进「硬规则可否决排序」清单，不做成加分项；本档已要求新增分项先回答能否被硬约束否决，家族冷却天然是否决式）。实案：429 集群与「claude→kimi 同上游换将失败」证明同族一损俱损，逐个试错等于烧预算。

### 缺口三：梯度冷却与恢复试用期

现状 30 分钟一刀切、期满满权复活。设计：同因连败按次升级（30min→2h→半天封顶），期满后**半权试用期**（在线信号打折计入）直至连续 N 次成功转正。与防饿死成对设计（红线 1）：无升级梯度的惩罚太软，无试用期的惩罚会饿死。

### 缺口四：值价比

均价已有软减分，不新增分项。在「成本与时延预算」的 usage 台账上派生 成功率/成本 档位画像，供 cascade 分流与排程参考；是否进权重表按「调参纪律」走前后差异证据，不凭感觉加分。

### 三条红线

1. **惩罚只改排序，不下狱**：被惩罚候选保留最低探索频次（ε 配额），否则早期失败者永远拿不到翻案数据，死锁。
2. **用户显式意志优先**：手工绑定链顺序与手动指定执行者压过一切自动降权；显式链内不做家族剔除（用户点名即自担）。
3. **新面孔保护期**：新接入 CLI/模型 30 天或前 K 次任务只记账不惩罚——历史战绩已有前 3 次线性加权，本条把保护延伸到冷却传导与家族连坐。

### 落地纪律

实施时按「调参纪律」走：同提交更新权重表与守卫（`test_candidate_scoring_standard.py`），给出前后差异证据（同类任务自动选路变化）；逐条失败归因按「并行会话协作纪律」表执行。
