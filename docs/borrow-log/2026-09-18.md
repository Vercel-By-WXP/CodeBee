## 四、补充调研：CodebuffAI/freebuff（12.3k★，用户点名，重点对直连对话/会话链）

同日追加。源码级深入：`agents/base-chat.ts`、`agents/editor/best-of-n/*`、`packages/agent-runtime/src/compact-history.ts`、`run-agent-step.ts` 结构。

**会话链路可借鉴点（按价值排序）**：
1. **换将后上下文超窗预检**（正确性问题）：freebuff 每步开始前用「本步将用的模型」的容量重新预算，超了先压缩再发请求（base-chat.ts handleSteps + CONTEXT_WINDOWS 表）。我们 `token_meter.pressure_ratio` 是响应式的（用量积累后才触发，未传 model 用 last_model），**换将切到小窗口模型的第一个请求没有预检，会直接被供应商拒**——已核实 pipeline.py:434-465 无 per-step 容量门。修法：步骤发起前按本步绑定模型容量算压力比，超阈值先走压缩。
2. **缓存感知压缩**（省成本）：prompt cache 还热（cacheExpiryMs 内）就不压缩，压缩会打爆服务端前缀缓存白白重算；DeepSeek 通道 15 分钟忘前缀的例外单独配（common/src/constants/compaction-policy.ts）。我们压缩无缓存维度。
3. **阈值实证**：他们实测本地估算 token 可能只有真实值一半（1.68–3.35 chars/token），预算比压到 0.4；未测模型默认给小窗口（131k）——"假设小了只是早压缩，假设大了线程卡死"。对照我们 DEFAULT_PRESSURE_THRESHOLD=0.8 + estimate_tokens 字符估算，偏乐观。
4. **Best-of-N 参考实现落地**（路线图①有谱了）：editor-multi-prompt.ts 每候选一个**不同策略提示词**（刻意制造多样性）→ 全部产出 unified diff → best-of-n-selector2 用强模型+高推理档收全部 diff+原始需求，结构化输出 {implementationId, reason, suggestedImprovements}；**败者精华回收**——selector 还要从落选实现里提取值得合并的好点子，下游"认真对待并落实"。评审顺序：正确性→简洁→规范→复用→diff 最小→可读。
5. **追问建议卡（suggest_followups）**：chat agent 每条回复末尾产出恰好 3 条建议追问（label + 用户第一人称 prompt），前端渲染成可点卡片直接发送。小改动，直接增强对话页。
6. **专职子 agent 分工**：主 chat 用便宜模型（deepseek-flash），推理外包 thinker、查网外包 researcher-web、找文件外包 file-explorer 家族（file-picker/code-searcher/glob-matcher）。我们 builtin_agent 是单体循环，可做「重推理/查资料」子步骤外包。
