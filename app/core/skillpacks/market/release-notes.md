# 版本发布说明撰写模板（市场包）

适用：发版时写 Release Notes / 更新公告 / changelog 的用户可读部分。
核心立场：**写给用户看，不是写给 git log 看**——用户不关心重构了哪个模块，
只关心「这次更新后我能多做什么、少烦什么、会坏什么」。

## 一、标准结构（顺序固定）
1. **一句话概览**：这版最值得用户知道的一件事；实在没有就写「稳定性修复」。
2. **新功能**：能做以前做不了的事。每条 = 功能名 + 用户收益 + 入口在哪。
3. **体验优化**：以前能做、现在更快 / 更顺 / 更省的事。
4. **问题修复**：写用户见过的**症状**（「修复导出 PDF 中文乱码」），
   不写内部成因（「修复字体子集化模块的编码偏移」）。
5. **升级注意事项 / 破坏性变更**：有则紧跟概览**置顶**（不按上面的顺序排），
   没有就省略此节。
6. **已知问题**：带着已知问题发版必须如实列出，并给临时绕过办法。

## 二、写作纪律
- 每条只说**一个行为变化**，动词开头、面向结果：「支持按标签筛选任务」，
  而不是「重构筛选服务并接入标签存储」。
- 收益优先于实现：先说用户能干什么，实现细节放括号或链接里。
- 数字具体化：「启动更快」要写成「冷启动从约 6 秒降到约 2 秒」；
  没有数据不要编数字。
- 不用内部术语：对用户写「登录更稳定」，不写「修复 OAuth2 refresh token 竞态」；
  这类内容放进面向开发者的附录小节。
- 每条尽量带出处：issue / PR / 需求单号，方便日后回溯。

## 三、破坏性变更的写法（最容易写砸的部分）
- 三要素齐全：**什么会坏**（哪个行为 / 接口 / 配置）、**影响谁**、**怎么办**
  （迁移步骤或替代写法，给可直接复制的示例）。
- 正面示例：
  > **升级注意**：`/api/tasks` 返回的 `status` 字段由中文改为枚举值
  > （`running` / `done` / `failed`）。依赖该字段的脚本需同步修改，
  > 新旧值对照表见帮助文档「status 迁移」一节。
- 「可能影响部分用户」这类模糊表述禁止——写清判定条件，让用户 10 秒内
  判断自己在不在影响范围内。

## 四、模板（可直接复制）
```
## vX.Y.Z 更新说明（YYYY-MM-DD）

概览：一句话说清这版最重要的事。

### 新功能
- 支持xxx：现在可以……（入口：设置 > xxx）(#123)

### 优化
- xxx 更快 / 更省：从……到……

### 修复
- 修复「用户看到的现象」(#456)

### 升级注意
- 变更点 → 影响谁 → 迁移步骤（附示例代码或对照表链接）

### 已知问题
- ……；临时绕过：……
```

## 五、反例对照
- 反例：「优化了底层性能。」→ 正例：「任务列表在 1 万条数据时加载时间从约 4 秒降到约 1 秒。」
- 反例：「修复若干问题。」→ 正例：「修复搜索结果偶发重复显示；修复深色模式下按钮文字不可读。」
- 反例：「接口升级，请注意适配。」→ 正例：按三要素写全（什么坏 / 影响谁 / 怎么办）。
- 反例：「重构核心模块。」→ 用户视角无行为变化的重构不进用户公告，放开发者 changelog。
