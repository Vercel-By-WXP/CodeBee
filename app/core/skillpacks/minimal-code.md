# 最少代码工程纪律（内置经验包）

来源：DietrichGebert/ponytail（MIT 许可）方法论蒸馏（2026-10-22 整合入 CodeBee）。
上游主张「像屋里最懒的资深开发一样思考」——最好的代码是没写出来的代码，用最少新代码
完整解决问题。本包固化其中可迁移的工程纪律，适用于代码开发/修复/重构/评审类任务。
适用边界：这是代码任务纪律，不约束写作类流程；上游自报的跑分（省代码 53% 等）为
自家评测，C 级证据，不作承诺。

## 一、动笔前先定改动面

- 读任务，再读要动的代码。列出本次改动必须到达的每一处：调用方、测试、夹具、配置、导出。
- 先想会破坏什么：会丢或会泄露的数据、会断掉的调用方。这些是范围；额外功能不是范围。

## 二、复用阶梯：按序取第一个能完整解决问题的

1. 它需要存在吗？没人要求的功能、选项和「灵活性」直接砍，一行点名即可。模糊需求
   （「做个 X」）交付只做核心活的最小版本。
2. 仓库里已有（helper/组件/服务/既有模式）？照周围代码的用法用它。
3. 标准库或平台自带能力？用它——除非项目有自己的实现（自家组件优先于原生件）。
4. 已安装的依赖里有？用它。绝不为几行代码新增依赖。
5. 一行就能让读的人看懂？就写一行。
6. 否则：能工作的最少代码。

## 三、执行纪律

- **对方案懒，对改动本身不懒**：任务需要的每一部分都要完成，包括被改动牵连的调用方、
  测试与夹具。砍范围不等于砍完整性。
- 不加没人要的抽象、包装、类型转换、选项、配置、样板和「以后用得上」的代码；值保持
  平台已给的原生形态；删除优于新增；保持代码库既有分层、接口与命名习惯。
- 最短可工作 diff 获胜——前提是改动面已经摸全；需要解码才能看懂的一行不是短。
- 只注释代码本身表达不了的 why，一行。
- Bug 修复先 grep 所有调用方，根因在共享代码修一次，不打补丁链。
- 搬移或合并的代码保留其原有的错误处理与校验，不借机精简掉。
- 同样大小的两个方案，选边界条件正确的那个。
- 非平凡新逻辑（新分支/循环/解析器/涉及钱或安全/整个新脚本）必须留一个小测试或
  assert 自检；平凡改动不需要。
- 带已知限制的捷径落一行注释，格式：`shortcut: <限制>, <何时升级>`。

## 四、永不省的红线

最少代码省的是范围，不是质量。以下无论多「懒」都不省：信任边界的输入校验、
防数据丢失的错误处理、安全、无障碍、真实环境校准，以及用户点名要的东西。

## 五、交付自查（评审视角）

- diff 逐块问：这块有人要吗？仓库里是不是已经有了？删掉会怎样？
- 回复末尾交代一两行：跳过了什么、没查什么、用户必须知道的风险。
- 评审他人 diff 时把「过度工程/重复造轮子」当检查视角，属软指引——不进硬闸，
  不因「写得比必要多」单独否决交付。
